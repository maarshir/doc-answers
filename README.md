# doc-answers

[![Тесты](https://github.com/maarshir/doc-answers/actions/workflows/tests.yml/badge.svg?branch=main)](https://github.com/maarshir/doc-answers/actions/workflows/tests.yml)

Отвечает на вопросы по папке со своими документами: находит подходящие куски текста и просит модель ответить строго по ним, со ссылкой на источник. Если ответа в документах нет, так и говорит.

Одной фразой для резюме: поиск по документам с ответами модели (RAG) без векторной базы, с проверкой ссылок на источник, отказом вместо выдумки и набором вопросов, который отдельно проверяет поиск и ответы модели.

## Зачем

Модель, которую спрашивают про внутренние правила компании, либо не знает их, либо уверенно придумывает. Если дать ей нужные куски документов прямо в запросе и потребовать ссылку на каждый факт, ответ можно проверить за секунду: открыть источник и посмотреть.

Проект сделан маленьким нарочно: чтобы каждую часть можно было прочитать и объяснить. Здесь нет векторной базы и фреймворков, весь путь от папки до ответа умещается в несколько небольших модулей на Питоне.

## Что готово

- Чтение папки: `.md` (с разбиением по заголовкам), `.txt`, `.pdf` (текстовый слой, по страницам). Битый или неподдерживаемый файл не роняет всё, а попадает в предупреждения.
- Нарезка на куски по абзацам, длинный абзац по предложениям, с перекрытием соседних кусков.
- Поиск BM25 по основам слов (стеммер Snowball для русского и английского). Если в документах нет ни одного слова из вопроса, модель не вызывается вовсе.
- Промпт с правилами: только по фрагментам, ссылка вида `[otpusk.md#2]` после каждого утверждения, точная фраза отказа.
- Проверка ответа: на какие куски есть ссылки, нет ли ссылок на куски, которых модели не давали, есть ли ссылка вообще.
- Демонстрационный режим без ключа: показывает найденные куски и прикидку цены запроса.
- Цена запроса через мой [token-counter](https://github.com/maarshir/token-counter): после ответа точная по токенам из ответа API, в демонстрационном режиме прикидка сверху.
- Набор из 15 вопросов к примерам документов (`eval/questions.yaml`): проверка поиска без ключа и выгрузка тех же вопросов в формат моего [prompt-arena](https://github.com/maarshir/prompt-arena), чтобы сравнить промпты на настоящей модели.
- 71 тест. Сеть в них подменена, ключ не нужен. На Гитхабе тесты идут на Python 3.10 и 3.12, плюс проверка, что prompt-arena принимает выгруженные файлы.

Настоящих ответов модели в репозитории пока нет: для них нужен ключ. Всё, что ниже показано как вывод программы, получено настоящим запуском без ключа.

## Как запустить

Нужен Python 3.10 или новее.

```bash
git clone https://github.com/maarshir/doc-answers.git
cd doc-answers
python -m venv .venv
source .venv/bin/activate      # на Windows: .venv\Scripts\activate
pip install -r requirements.txt
pytest
```

### Вопрос без ключа

```bash
python -m doc_answers ask "Как быстро дежурный должен ответить на сбой ночью?" --k 2
```

По умолчанию ищет в `examples/docs`: это вымышленная памятка сотрудника вымышленной студии, написанная для этого репозитория. Настоящий вывод:

```
Демонстрационный режим (нет ANTHROPIC_API_KEY): модель не вызывалась.
Вот куски, которые получила бы модель, лучшие сверху:

1. [dezhurstva.md#2] dezhurstva.md, Дежурства по сайтам клиентов / Сроки реакции  (счёт 5.86, совпали: дежурн, сбо, ноч)
   На сообщение о сбое дежурный отвечает в течение 15 минут в рабочее время и в течение одного
   часа ночью и в выходные.

   Если сайт клиента не открывается совсем, дежурный сразу подключает руководителя направления,
   не дожидаясь, пока починит сам.

2. [dezhurstva.md#4] dezhurstva.md, Дежурства по сайтам клиентов / После сбоя  (счёт 4.69, совпали: дежурн, сбо)
   После каждого сбоя дежурный в течение трёх рабочих дней пишет короткий разбор: что случилось,
   почему, что сделали и что поменять, чтобы не повторилось. Виноватых в разборе не ищут.


≈475 токенов на входе (прикидка без токенизатора), не больше 700 на выходе. С ключом запрос к claude-haiku-4-5 стоил бы не больше ≈$0.003975.
```

«Совпали» показывает основы слов из вопроса, которые нашлись в куске: так видно, почему поиск выбрал именно его.

### Вопрос с ключом

```bash
cp .env.example .env           # и впишите в .env свой ANTHROPIC_API_KEY
python -m doc_answers ask "Сколько дней отпуска в году?"
python -m doc_answers ask "Что делать, если сломался ноутбук?" --docs путь/к/своей/папке
```

Модель ответит текстом со ссылками вида `[otpusk.md#1]`, ниже будет список источников с файлом и разделом, число токенов и цена. Если модель сослалась на кусок, которого ей не давали, или не сослалась ни на что, под ответом будет предупреждение.

Параметры: `--docs` (папка), `--k` (сколько кусков отдать модели, по умолчанию 4), `--size` и `--overlap` (размер куска и перекрытие в символах, по умолчанию 600 и 120), `--model` (по умолчанию `DOC_ANSWERS_MODEL` из `.env` или `claude-haiku-4-5`), `--no-model` (не вызывать модель даже с ключом), `--show-prompt` (показать сообщение, которое уходит модели), `--prices` (свой файл цен для token-counter).

## Как проверить качество

Ответ по документам ломается в двух местах, и проверять их лучше отдельно.

**Поиск: нашёлся ли кусок с ответом.** Проверяется без модели и бесплатно:

```bash
python -m doc_answers search-eval
```

Для каждого вопроса из `eval/questions.yaml` показывает место куска с ответом в выдаче. Кусок считается верным, только если он из нужного файла и в нём есть все ожидаемые факты: соседний раздел того же файла не засчитывается. Настоящий итог на примерах:

```
Кусок с ответом на первом месте: 12 из 12, среди первых 4: 12 из 12.
Вопросы без ответа: 3, из них поиск сам отсеял 2; остальные должна отсеять модель (это проверяет prompt-arena).
```

Честно: примеры маленькие и вопросы к ним простые, поэтому 12 из 12 говорит только о том, что ничего не сломано. С кусками по 200 символов (`--size 200 --overlap 40`) нужный кусок на первом месте уже в 10 из 12 случаев. Эта проверка стоит в CI: если правка нарезки или поиска потеряет ответ, тесты покажут, на каком вопросе.

**Модель: ответила ли по найденному, со ссылкой и без выдумки.** Для этого вопросы выгружаются в формат [prompt-arena](https://github.com/maarshir/prompt-arena):

```bash
python -m doc_answers export-arena      # пишет eval/arena/prompts.yaml и eval/arena/cases.yaml
```

Входом каждой задачи служит ровно то сообщение, которое doc-answers отправил бы модели. Проверки: в ответе есть факт и имя файла из ссылки, и нет отказа; у вопроса без ответа должна быть фраза отказа. Вариантов промпта два: `strict` (промпт этого проекта) и `plain` (тот же договор о формате, но без правил), чтобы увидеть, что правила дают на деле. Файлы не хранятся в репозитории, а создаются из кода и вопросов, поэтому не расходятся с ними; в CI их проверяет настоящий загрузчик prompt-arena. Прогон с ключом из папки prompt-arena:

```bash
python run.py --prompts ../doc-answers/eval/arena/prompts.yaml \
              --cases ../doc-answers/eval/arena/cases.yaml --model claude-haiku-4-5
```

Результатов этого прогона здесь пока нет, они появятся после первого запуска с ключом.

## Технологии и почему они

- **BM25 вместо векторного поиска.** Эмбеддинги требуют либо ключа к ещё одному API, либо скачивания модели на сотни мегабайт, а их результат трудно объяснить. BM25 работает без сети за миллисекунды, и по каждому куску видно, какие слова совпали. Цена этого решения известна: синонимы («ноутбук» и «компьютер») поиск не свяжет.
- **snowballstemmer** для основ слов. Без него «отпуска» не находило бы «Отпуск». Это маленькая библиотека на чистом Питоне без зависимостей.
- **pypdf** для текста из PDF. Сканы без текстового слоя дают пустоту, распознавания текста здесь нет, и программа об этом предупреждает.
- **httpx** для запроса к Anthropic API напрямую, без SDK: запрос один, и так видно, что именно уходит в модель. Повторы только при перегрузке, сбое сервера или обрыве сети, пауза растёт с разбросом.
- **token-counter** для цены, закреплён на номере коммита: правка цен там не меняет тихо цифры здесь.
- **claude-haiku-4-5** по умолчанию: задача (прочитать четыре куска и пересказать нужное) не требует большой модели, а стоит она в разы дешевле.

## Что было непросто

- **Куда резать.** Слишком маленький кусок теряет смысл: «в течение одного часа ночью» без предыдущей фразы непонятно к чему относится. Слишком большой занимает место других кусков и размывает счёт поиска. Решение: резать по границам смысла (заголовок, абзац, предложение, и только в крайнем случае по словам), а для перекрытия брать с конца предыдущего куска только целые предложения. Оборванная фраза в начале куска сбивает и поиск, и модель.
- **Заголовок это часть текста.** Кусок часто не повторяет тему своего раздела: в разделе «Оборудование / Мониторы и остальное» слова «оборудование» в тексте нет. Поэтому цепочка заголовков участвует в поиске и уходит модели вместе с куском, а в ссылке на источник видно не только файл, но и раздел.
- **Не звать модель, если не на что опереться.** Если в документах нет ни одного слова из вопроса, любой ответ модели был бы выдумкой за наши деньги. Такой вопрос отсекается до модели. Но это ловит только совсем посторонние вопросы: «сколько дней больничного» находит куски про отпуск по слову «дней», и отказаться здесь должна уже модель. Поэтому в наборе есть оба случая.
- **Модели нельзя верить на слово про источники.** Модель может сослаться на кусок, которого не видела, или не сослаться ни на что. После ответа ссылки проверяются кодом по списку отданных кусков, и о проблеме пишется прямо под ответом.
- **Отказ одной точной фразой.** Если разрешить модели отказываться своими словами, программа не отличит отказ от ответа. Фраза живёт в одной константе, из неё собираются промпт, разбор ответа и проверки для prompt-arena.
- **Стеммер не всесилен.** Snowball не сводит беглые гласные: «дней» и «дни» у него разные основы. Это записано тестом, чтобы ограничение было видно, а не всплывало неожиданно.

## Что дальше

- Сравнить настройки поиска (размер кусков, число кусков) на более трудном наборе вопросов и записать выводы сюда.
- Первый настоящий прогон двух промптов через prompt-arena и его итог в этом README.
- Показывать в ответе не только файл и раздел, но и цитату, на которую опирается утверждение.
- Для больших папок хранить индекс на диске, а не строить заново при каждом вопросе.
- Попробовать гибридный поиск (BM25 и эмбеддинги вместе) и сравнить на том же наборе вопросов, стоит ли он усложнения.
